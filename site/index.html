How it works

namespace

A blockchain for names, anchored in Bitcoin. Its only asset is names: there are no coins, no fees and no block rewards. Bitcoin decides which blocks count, and the rules decide who gets which name.

1Overview

Names are 1–63 characters of a-z, 0-9 and -, each mapping to an owner's BIP340 public key. The chain records who owns what and nothing else.

The chain has no miners or validators of its own. Each namespace block is anchored by a Bitcoin transaction that commits to its hash. Bitcoin's proof of work orders the anchors, and every node applies the same rules to the anchored blocks, so they all agree on the same names.

BitcoinOrders anchors and limits them to one every 3 Bitcoin blocks. It knows nothing about names.
BuildersAssemble namespace blocks, sign them, and pay the Bitcoin fee to anchor them.
NodesFollow Bitcoin, collect block bodies, apply the rules, and serve lookups and proofs.
OwnersHold a key per name. They renew and transfer names by signing.

2Anchoring in Bitcoin

Namespace blocks are blind merge-mined using Ruben Somsen's spacechain design. A chain of Bitcoin transactions is signed in advance and then the signing key is deleted. Each covenant transaction Ti spends the previous one's covenant output and creates two outputs:

  • a covenant output, which only Ti+1 can spend, and
  • a zero-value pay-to-anchor (P2A) output, which anyone can spend.

Covenant transactions pay no fee. To anchor a block, a builder broadcasts Ti together with a child that spends its P2A output and carries OP_RETURN "NSPC" <block hash>. The child pays the fee for both. Only one child can spend the P2A output, so each covenant transaction anchors at most one block, and Bitcoin miners just take the child that pays the most.

Covenant transactions are TRUC (version 3), and their P2A output is ephemeral dust, so they relay only as a package with a child that spends it. Builders compete for a slot by replacing each other's child with one that pays more.

Every rule counts namespace block heights, not Bitcoin heights, so a block is valid or invalid no matter which Bitcoin block its anchor lands in.

3Builders

A builder takes transactions from its node's mempool, assembles the next block, signs it, and anchors it. Each block header names the builder's BIP340 key, and the block carries the builder's signature over the header hash. A block with a bad signature is invalid. A node keeps its builder key in builder.key in its data directory.

The chain has no fees, so nothing on it pays builders. Users pay a builder some other way, outside the protocol: over Lightning, say, or with a Bitcoin payment. Builders spend what they collect on the Bitcoin fee for their anchor. The highest-paying child gets the slot, so a builder that collects more can outbid the others.

Getting a block anchored is the only scarce thing a builder has. Whoever wins a slot decides what goes into that namespace block, including which free names it announces (see announcements).

4Fork choice

Bitcoin orders the anchors, but each header names its own parent, so anchored blocks form a tree rooted at genesis. A block is eligible when:

  • it is anchored, and its first anchor comes after its parent's,
  • its body is known and its height is one more than its parent's,
  • it has been checked and is valid, and
  • its parent is genesis or eligible.

The tip is the highest eligible block. Ties go to the block anchored first.

If a builder anchors a block but never publishes its body, that block isn't eligible, so the chain stalls there. Other builders get past it by anchoring blocks on its parent. Once that branch is longer, the withheld block is orphaned. A Bitcoin reorg undoes the anchors it removes and the namespace blocks built on them, and their transactions go back to the mempool.

5Names

A name record holds the owner key, the height it was registered at, the height it expires at, and a sequence number.

TransactionWho sends itWhat it does
Announceanyone; the block's builder owns itOpens a free name. The announcement belongs to the builder of the block it is in.
Registeranyone; only the announcing builder can include itGives an announced name to an owner key.
Renewowner, signedMoves expiry to expiry_period blocks from now.
Transferowner, signedMoves the name to a new owner key.

Renewals and transfers are Schnorr-signed over (name, registered_at, seq). seq goes up with each one, so a signature can't be replayed. registered_at ties a signature to one registration, so an old owner's signature stops working if the name expires and someone registers it again.

A name expires expiry_period (52,560) blocks, about three years, after it was registered or last renewed. An expired name has to be announced again before anyone can register it.

6Announcements

Every registration starts with an announcement, and the announcement belongs to the builder of the block it is in. Only that builder can register the name, and it gets exactly one chance:

  1. The name is announced in a block at height a, built by builder B.
  2. Until a + announce_delay, no one can register it. B's blocks in this period don't count.
  3. B's first block at or after a + announce_delay can register it to any owner. Blocks by other builders don't use up B's chance.
  4. If that block doesn't register it, the announcement lapses and can't be registered.
  5. At a + 2 × announce_delay an unregistered announcement is released, and anyone can announce the name again.

Why it works this way

A Bitcoin anchor buys a whole block, so builders bid on the total value of everything in it. If any builder could register any announced name, a builder that wins a slot thanks to a valuable name like bob could also take oooop, even though someone else bid more for oooop through a different builder. Tying each name to its announcing builder means a slot won on one name can't take names other builders announced.

So the contest for a name happens when it's announced: whoever wins a slot while a name is free can claim it, up to the tier caps. Users who want that name then buy it from the announcing builder.

The mempool accepts a registration as long as its announcing builder could include it, so other nodes relay it on to that builder.

7Announcement tiers

Announcements are rate-limited, and shorter names open later. A name's tier is how many characters shorter than 10 it is: names of 10 or more characters are tier 0, 9 characters is tier 1, and 1 character is tier 9.

When a tier reaches 16 per block, the next tier opens. Tier 0 starts at stage 3, so it allows 3 per block at launch. Each tier takes six stages, about 18 months, to reach its cap:

The caps limit how many names a slot's builder can claim. That matters most while a tier is opening, when its best names are still free and the tier allows only one announcement every few blocks. Registrations have no cap of their own, since each one needs an announcement. A block can hold at most max_txs_per_block transactions of any kind.

8State commitment & proofs

Each header carries a state_root: the root of a sparse Merkle tree over every name record and pending announcement after the block. A block whose root doesn't match the state it produces is invalid.

Given a header, anyone can check a proof that a name has a given record, or has none:

GET /proof/<name>     # record + Merkle proof against the tip's state_root
ns proof alice         # fetches and verifies it

A node snapshots the state every 1,000 blocks and on shutdown. On startup it loads the newest snapshot that's on the best chain and matches its block's state_root, then replays from there. A reorg deeper than the snapshot falls back to replaying from genesis.

10Running it

The code is three Rust crates. core holds the consensus rules and does no IO. node is namespaced: it follows Bitcoin, stores blocks, talks to peers over iroh, and serves a local HTTP API. cli is ns, the wallet and builder tool.

# Once per chain: make the covenant.
ns covenant keygen --key-out cov.key --network regtest   # prints an address; fund it
ns covenant sign --key cov.key --funding <txid>:<vout> --amount <sats> \
  --count 10000 --out covenant.json                       # deletes cov.key

namespaced --network regtest \
  --bitcoin-backend esplora --bitcoin-url http://localhost:3000 \
  --covenant-start <txid>:<vout> --covenant-start-height <h>

ns keygen
ns announce alice    # owned by the builder whose block includes it
ns register alice    # that builder can include it announce_delay blocks later
ns lookup alice
ns proof alice

# Builders: build a block and anchor it.
ns anchor --chain covenant.json --network regtest --fee-rate 2 \
  --utxo <txid>:<vout> --utxo-amount <sats> --utxo-address <addr> --change <addr>
bitcoin-cli walletprocesspsbt <psbt>
ns finalize <signed psbt>
bitcoin-cli submitpackage '["<covenant tx>", "<child>"]'

11Open problems

These are known weaknesses of the current design, not yet solved:

  • Builders are trusted with payments. A payment to a builder can't depend on what ends up in a namespace block, because Bitcoin can't see namespace state. A builder can take payment and then not register the name, or register it to someone else.
  • Picks from different tiers share a block. One slot can allow announcements in several tiers at once, so a single fee bid covers all of them. Once every tier is at its cap, a slot can claim up to 160 names.
  • Builders can hold names. After a release, the same builder can announce the name again, under a new key if it wants. Each re-announcement uses one of the tier's announcement slots, which is expensive while a tier is opening and cheap once it's at its cap.
  • Bitcoin miners get the last look. The miner who finds a block sees every competing child and can anchor its own block instead, giving up only the best fee it skipped.
  • No light client yet. Proofs are checked against a header from a node. A client that follows headers through their Bitcoin anchors alone couldn't tell whether a block is valid, because eligibility depends on the block's contents.
